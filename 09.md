# Incident & Diagnostic Report: Production Database Pool Starvation & Random User Logouts

**Date:** September 8, 2026  
**Environment:** Production (`infra:PDD-LMB-PRD`)  
**Namespace:** `middleware-prd-ns`  
**Applications Impacted:** `backoffice-app` (https://lmbbackoffice.lulumoney.com/), and dependent microservices  
**Database:** `lmb_management` (`lmbdb-prd.lulumoney.com:5432`) via PgBouncer  

---

## 1. Executive Summary

During investigation of repeated health probe timeouts (`/api/backoffice/check/ready`) and user reports of being randomly logged out after logging into the Backoffice portal, the following root causes were identified:

1. **The Database Storage is NOT Full:**
   * Disk storage is completely normal. Total size of `lmb_management` is **~3.8 GB** (3,815 MB).
   * Table bloat and dead tuple counts are healthy.

2. **The Database Connection Pool IS Starved / Saturated (Root Cause):**
   * PgBouncer is configured with a maximum pool of **50 connections** for `lmb_management`.
   * **42 out of 50 connections** (84%) have been permanently frozen in an `idle in transaction` state with the query `BEGIN;` for up to **4 days, 1 hour** (since the September 4 deployment).
   * Only **5 to 7 connections** remain to handle all production traffic across all 5 replicas of `backoffice-app`, `businessmanagement`, `corporateapp`, and other services.

3. **Why Users Get Logged Out:**
   * Every API request checks the user's session and permissions via 6�7 database queries in `jwt.js`.
   * When traffic spikes, the pool runs out of connections, throwing `KnexTimeoutError: Knex: Timeout acquiring a connection. The pool is probably full.`
   * The application's `catch` block catches this DB error as `"JWT validation failed"` and responds with **HTTP 401 Unauthorized**.
   * The Backoffice frontend receives the 401 status, invalidates the token, and redirects the user to the login screen.

## 3. Technical Mechanism of Failure

1. **PgBouncer Pinned Connections:**
   PgBouncer operates in `transaction` pool mode. When any service executes `BEGIN;`, PgBouncer binds that client connection directly to a dedicated backend PostgreSQL connection until `COMMIT` or `ROLLBACK` is issued.
2. **Transaction Leak:**
   Certain application endpoints create manual transactions using `const tranx = await db.transaction();`. When an unhandled error or early exit occurs without reaching `await tranx.rollback()`, the transaction is never closed.
3. **No Automatic Timeout in PostgreSQL:**
   PostgreSQL has `idle_in_transaction_session_timeout = 0` (disabled). PostgreSQL will keep an abandoned transaction open indefinitely.
4. **Cascading Pool Starvation:**
   Over the last 4 days, 42 connections leaked one by one. With only 5�7 connections remaining, ordinary database traffic causes connection wait times in PgBouncer to exceed 2�10 seconds.
5. **False Authentication Failures:**
   In `jwt.js`, the authentication middleware wraps all user validation logic in a `try/catch`. When `getStaffUser` fails due to `KnexTimeoutError`, the catch block logs `"JWT validation failed"` and responds with `HTTP 401 Unauthorized`. The web browser client receives 401 and logs the user out.

## 4. Remediation Steps

### Step 1: Immediate Relief (Kill Orphaned Sessions)
Execute the following query directly on PostgreSQL (via DBA tool / psql) to immediately terminate all transactions that have been idle for more than 15 minutes:

```sql
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND datname = 'lmb_management'
  AND (now() - state_change) > interval '15 minutes';
```
*Effect:* Instantly frees 42 connections in PgBouncer, restoring full capacity (50/50 available) and stopping random logouts immediately.

---

### Step 2: Prevent Future Leaks in PostgreSQL & PgBouncer

1. **Enable Idle Transaction Timeout in PostgreSQL:**
   Configure PostgreSQL to automatically terminate transactions that remain idle for more than 60 seconds:
   ```sql
   ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
   SELECT pg_reload_conf();
   ```

2. **Configure PgBouncer Timeouts:**
   In `pgbouncer-config` or deployment settings:
   ```ini
   idle_transaction_timeout = 60
   server_idle_timeout = 60
   ```

---

### Step 3: Kubernetes & Application Resilience

1. **Increase Readiness Probe Timeout:**
   In `backoffice-app` deployment manifest:
   ```yaml
   readinessProbe:
     httpGet:
       path: /api/backoffice/check/ready
       port: 6106
     timeoutSeconds: 5   # Increased from 2 to 5 seconds
     periodSeconds: 10   # Increased from 5 to 10 seconds
   ```

2. **Improve Error Differentiation in `jwt.js`:**
   In `jwt.js`, distinguish between invalid credentials (return 401) and internal database connection errors (return 500 or 503) so temporary database delays do not force users out of their sessions:
   ```javascript
   catch (err) {
       if (err.message && err.message.includes("Timeout acquiring a connection")) {
           logger.error("DB connection timeout during auth check", err);
           return res.status(503).send({ error: true, message: "Service temporarily unavailable, please retry." });
       }
       logger.warn("JWT validation failed", { ip: req.ip, error: err.message });
       return res.status(401).send({ error: true, message: "Unauthorized" });
   }
   ```

3. **Code Audit for `db.transaction()`:**
   Ensure all services using manual transactions (`const tranx = await db.transaction()`) are refactored to Knex's callback pattern:
   ```javascript
   await db.transaction(async (trx) => {
       // Knex automatically commits on success and rolls back on exception
   });
   ```

### 5.6 Comprehensive Audit: Bottlenecks & Architectural Flaws with Current Setup

| Category | Current Production Configuration | Severity | Risk & Impact |
| :--- | :--- | :--- | :--- |
| **Database Sizing Inversion** | PostgreSQL Flexible Server is `Standard_D2ds_v4` (**2 vCPUs, 8 GiB RAM**) serving 24+ container pods allocated 50+ vCPUs | **CRITICAL** | Database CPU is pinned at 94% - 98.6%. 2 vCPUs cannot handle lock arbitrations, indexing, and 84 concurrent connections. |
| **PgBouncer Disabled** | Built-in PgBouncer is disabled on PostgreSQL (`pgbouncer.enabled = false`) | **HIGH** | Every container maintains its own direct Knex connection pool. High connection count wastes PostgreSQL memory and CPU context switching. |
| **High Availability Disabled** | High Availability is `Disabled` on `zb-psql-pp-prd-eastus` | **HIGH** | Single point of failure (SPOF) for the entire production banking platform. |
| **Missing Lock & Session Timeouts** | `idle_in_transaction_session_timeout = 0`, `lock_timeout = 0`, `statement_timeout = 0` | **CRITICAL** | Abandoned transactions hold row/table locks forever. Queries wait up to 12.4 minutes instead of failing fast and recovering. |
| **Autoscaling Blind Spot** | Only `concurrentRequests = 10` HTTP rule configured; no CPU, Memory, or Latency rules | **HIGH** | Slow transactions hanging for 60s never scale out because single-user request concurrency remains under 10. |
| **Code Transaction Scope** | Explicit DB transactions (`const tranx = await connection.transaction()`) wrap outbound HTTP network calls (`sendCreatePaymentRequest`, `disableAuthenticatorApp`) | **CRITICAL** | Holding row locks open while awaiting external HTTP APIs causes cascading thread locks across all microservices. |
| **Missing Idempotency Guard** | Payment endpoints lack Redis deduplication locks on `(user_id + amount + beneficiary)` | **CRITICAL** | User re-clicks on slow responses trigger duplicate multi-million-dollar banking transfers. |

### 5.7 Actionable Remediation Plan

1. **Code Fix (Immediate):**
   * Commit `tranx.commit()` immediately after updating the `otps` row (Line 736) in `otpService.ts`. Never execute outbound HTTP calls (`sendCreatePaymentRequest`, `checkForApproval`, `disableAuthenticatorApp`) inside a database transaction.
   * Add a 5-minute Redis-backed idempotency lock in `fintech_business_management` on payment request IDs.
2. **Database Engine Sizing & Safety Parameters:**
   * **Scale PostgreSQL Instance:** Upgrade `zb-psql-pp-prd-eastus` from `Standard_D2ds_v4` (2 vCPU) to at least **`Standard_D8ds_v4` (8 vCPUs, 32 GiB RAM)** or `Standard_E8ds_v4` (Memory Optimized).
   * **Enable PgBouncer:** Set `pgbouncer.enabled = true` on the Flexible Server to pool connections across all microservices.
   * **Set Defensive Timeouts:**
     ```sql
     ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
     ALTER SYSTEM SET lock_timeout = '10s';
     ALTER SYSTEM SET statement_timeout = '60s';
     SELECT pg_reload_conf();
     ```
   * **Enable High Availability:** Enable Zone-Redundant High Availability on `zb-psql-pp-prd-eastus`.
3. **Autoscaling Optimization:**
   * Add CPU and Memory scaling rules to Azure Container Apps (e.g. scale up when average CPU > 70% or average Memory > 75%).
   * Reduce HTTP concurrency threshold from 10 to 5 for critical transactional services (`notifications-mgnt`, `business-management`).
