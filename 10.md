## 1. Executive Summary: What Went Wrong (In Simple Words)

On September 3, 2026, an operator in the Back Office portal submitted a manual internal transfer of **$1,500,000.00 USD** for Nexo Capital Inc. The portal froze for ~60 seconds and returned `HTTP 410 ("Code cannot be accepted")`. Believing the payment failed, the operator requested a fresh OTP and submitted again. Both transfers went through, resulting in **two duplicate transfers of $1,500,000.00 USD each ($3,000,000.00 total)** processed by Tuum core banking (`PAYM-212370` and `PAYM-212372`).

### The 5 Compounding Breakdowns:
1. **The Code Defect (`otpService.ts`):** An explicit database transaction (`tranx`) placed a row lock on the `otps` table row and was held open for **11 to 60 seconds** while the backend waited for outbound HTTP API calls (`sendCreatePaymentRequest`, `checkForApproval`).
2. **The Hardware Sizing Inversion:** The central production PostgreSQL database runs on a tiny **`Standard_D2ds_v4` instance (ONLY 2 vCPUs and 8 GiB RAM)**. While microservices pods were assigned over 50+ vCPUs, the 2-vCPU database was pinned at **93.2% to 98.63% CPU**, stalling query execution across all services.
3. **Missing Database Safeguards:** PostgreSQL parameters `lock_timeout = 0`, `statement_timeout = 0`, and `idle_in_transaction_session_timeout = 0` allowed blocked queries to wait **indefinitely (up to 12.46 minutes / 747 seconds)** instead of failing fast.
4. **The False Error (HTTP 410):** Request #1 immediately marked the OTP as consumed in Redis (`is_active = false`) before processing the payment. When the user re-clicked or retried, Request #2 hit Redis, saw `is_active = false`, and returned `HTTP 410 Gone`.
5. **Autoscaling Blind Spot:** Autoscaling rules only trigger when concurrent requests exceed **10 per pod**. Because single-operator submissions had a concurrency of only 1 to 2, **the autoscaler never added replicas**, keeping all services locked at 2 pods.

## 7. Verified Code Fix: Pull Request #313 (`hotFix/duplicatePayments`)

Latest code was pulled from `origin/sandbox_qa` (Merged PR #313). Inspection of `fintech_notifications_management` confirms that the development team has implemented the permanent code-level fix:

### A. Key Code Fixes Verified in `src/services/otp/otpService.ts`:

#### 1. Immediate Transaction Commit (Releases Database Lock in < 10ms)
Lines 785–791 in updated `otpService.ts`:
```typescript
const otpUpdateStart = Date.now();
await OtpModel.query(tranx).update(queryParams).where("id", response.id);

// FIX IMPLEMENTED: Transaction committed immediately after DB write!
await tranx.commit();
logStepDuration("updateOtpRecord + commit", otpUpdateStart);
```
* **Impact:** The exclusive PostgreSQL row lock on the `otps` table is released immediately (< 10 ms). Outbound HTTP requests (`checkForApproval`, `sendCreatePaymentRequest`, `disableAuthenticatorApp`) are now executed **outside** the database transaction, eliminating the 11–60 second database freeze.

#### 2. Redis Distributed Locking Implemented (`distributedLock.ts`)
Lines 595–615 in updated `otpService.ts`:
```typescript
// FIX IMPLEMENTED: Distributed lock acquired before OTP verification
const lockAcquireStart = Date.now();
try {
    ({ lockValue } = await acquireLock(lockKey, config.otp.lockTtlSeconds * 1000));
    logStepDuration("acquireLock", lockAcquireStart);
} catch (error: any) {
    if (error instanceof LockAcquisitionError && error.reason === "HELD") {
        logger.warn(`[verifyOTP] OTP verification already in progress for token ${payload.otp_token}`);
        throw new createHttpError.Conflict(
            "OTP verification already in progress, please try again in a moment."
        );
    }
    throw new createHttpError.ServiceUnavailable(
        "Unable to process OTP verification right now, please try again shortly."
    );
}
```
* **Impact:** If a user double-clicks or retries while request #1 is processing, the system returns **`HTTP 409 Conflict ("OTP verification already in progress")`** instead of throwing `HTTP 410 Gone` or locking the user out for 24 hours.

#### 3. 1:1 Link Between OTP and Payment Record
Lines 910–920 in updated `otpService.ts`:
```typescript
// FIX IMPLEMENTED: Store otp_id directly on BeneficiaryPaymentsModel
if (paymentResponse?.id) {
    const linkOtpToPaymentStart = Date.now();
    await BeneficiaryPaymentsModel.query()
        .update({ otp_id: response.id })
        .where("id", paymentResponse.id);
    logStepDuration("linkOtpToPayment", linkOtpToPaymentStart);
}
```

## 9. How to Perform All Remaining Changes in Azure Portal UI (No CLI Needed)

You do **not** need to run any commands in terminal. Every change below can be performed directly in the Azure Portal UI:

### Step 1: Scale Database Compute Size in the UI
1. Open **[portal.azure.com](https://portal.azure.com/)**.
2. Go to: **`zb-psql-pp-prd-eastus`**.
3. On the left sidebar menu under **Settings**, click **Compute + storage**.
4. Under **Compute tier**, keep **General Purpose**.
5. Under **Compute size**, click the dropdown and select: **`Standard_D8ds_v4 (8 vCPUs, 32 GiB memory)`**.
6. Under **Storage size**, select: **`256 GiB`** or **`512 GiB`**.
7. Click the **Save** button at the bottom. *(Azure will apply the new tier with a brief 1–2 minute failover).*

### Step 2: Enable Built-In PgBouncer in the UI
1. In `zb-psql-pp-prd-eastus`, left menu under **Settings**, click **Server parameters**.
2. In the search box, type: **`pgbouncer.enabled`**.
3. In the **Value** dropdown, change `false` to **`true`**.
4. Click the **Save** button at the top left.

### Step 3: Set Defensive Timeouts in the UI (No SQL Needed!)
1. In the same **Server parameters** search box, type: **`idle_in_transaction_session_timeout`**.
   * Change value from `0` to **`30000`** (30 seconds in milliseconds).
2. In the search box, type: **`lock_timeout`**.
   * Change value from `0` to **`10000`** (10 seconds in milliseconds).
3. In the search box, type: **`statement_timeout`**.
   * Change value from `0` to **`60000`** (60 seconds in milliseconds).
4. Click the **Save** button at the top left.

### Step 4: Enable Zone-Redundant High Availability in the UI
1. In `zb-psql-pp-prd-eastus`, left menu under **Settings**, click **High availability**.
2. Check the box for **Enable High Availability**.
3. Select **Zone-Redundant High Availability**.
4. Click **Save**.

### Step 5: Update Container App Autoscaling in the UI
1. In Azure Portal, go to: **`zb-prod-notifications-mgnt-001`** (and `zb-prod-business-management-001`).
2. Left menu under **Application**, click **Scale and replicas**.
3. Under **Scale rules**, click **Edit** on `http-scaler`:
   * Change **Concurrent requests** from `10` to **`5`**.
4. Click **+ Add rule**:
   * **Rule name:** `cpu-scaler`
   * **Type:** `Custom` -> Select `CPU utilization` -> Set threshold to **`70%`**.
5. Click **+ Add rule**:
   * **Rule name:** `memory-scaler`
   * **Type:** `Custom` -> Select `Memory utilization` -> Set threshold to **`75%`**.
6. Click **Save**.
