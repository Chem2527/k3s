## 1. Executive Summary: What Went Wrong (In Simple Words)

On September 3, 2026, an operator in the Back Office portal submitted a manual internal transfer of **$1,500,000.00 USD** for Nexo Capital Inc. The portal froze for ~60 seconds and returned `HTTP 410 ("Code cannot be accepted")`. Believing the payment failed, the operator requested a fresh OTP and submitted again. Both transfers went through, resulting in **two duplicate transfers of $1,500,000.00 USD each ($3,000,000.00 total)** processed by Tuum core banking (`PAYM-212370` and `PAYM-212372`).

### The 5 Compounding Breakdowns:
1. **The Code Defect (`otpService.ts`):** An explicit database transaction (`tranx`) placed a row lock on the `otps` table row and was held open for **11 to 60 seconds** while the backend waited for outbound HTTP API calls (`sendCreatePaymentRequest`, `checkForApproval`).
2. **The Hardware Sizing Inversion:** The central production PostgreSQL database runs on a tiny **`Standard_D2ds_v4` instance (ONLY 2 vCPUs and 8 GiB RAM)**. While microservices pods were assigned over 50+ vCPUs, the 2-vCPU database was pinned at **93.2% to 98.63% CPU**, stalling query execution across all services.
3. **Missing Database Safeguards:** PostgreSQL parameters `lock_timeout = 0`, `statement_timeout = 0`, and `idle_in_transaction_session_timeout = 0` allowed blocked queries to wait **indefinitely (up to 12.46 minutes / 747 seconds)** instead of failing fast.
4. **The False Error (HTTP 410):** Request #1 immediately marked the OTP as consumed in Redis (`is_active = false`) before processing the payment. When the user re-clicked or retried, Request #2 hit Redis, saw `is_active = false`, and returned `HTTP 410 Gone`.
5. **Autoscaling Blind Spot:** Autoscaling rules only trigger when concurrent requests exceed **10 per pod**. Because single-operator submissions had a concurrency of only 1 to 2, **the autoscaler never added replicas**, keeping all services locked at 2 pods.

## 9. Summary: What Went Wrong & What Needs to Be Added / Modified

### A. What Went Wrong (Root Causes Summary)
1. **Uncommitted DB Transaction Holding Row Locks:** `tranx` stayed open across slow network HTTP calls, freezing all OTP verification queries.
2. **Premature Redis Invalidation:** Line 674 set `is_active = false` immediately. When the user re-submitted during the freeze, Request #2 returned `410 Gone`.
3. **Missing Payment Idempotency:** The backend did not check whether a payment with the same parameters was already in-flight, allowing duplicate execution of $1.5M transfers.
4. **Database Sizing Inversion:** A central 2-vCPU database was crushed by 50+ microservice container vCPUs.
5. **Autoscaling Blind Spot:** Autoscaler only looked for concurrent requests > 10, completely blind to 60-second hanging requests.
6. **Zero Defensive Timeouts:** PostgreSQL `lock_timeout = 0` let queries wait up to 12.4 minutes without failing.

---

### B. What Needs to Be Added or Modified (Actionable Blueprint)

#### 1. Codebase Modifications (Immediate Priority)

##### In `fintech_notifications_management` (`src/services/otp/otpService.ts`):
* **Action:** Move `await tranx.commit();` immediately after the OTP update at Line 736. Never wrap outbound HTTP calls in a database transaction.
* **Diff:**
```diff
  await OtpModel.query(tranx).update(queryParams).where("id", response.id);
+ await tranx.commit(); // Release DB lock immediately (< 10ms)!

  if (source === "PAYMENT" && payload?.payment_request_params) {
      const isApprovalFlow = await checkForApproval(payload);
      const paymentResponse = await sendCreatePaymentRequest(payload, authToken);
      responseObj.data = paymentResponse;
  }

- await tranx.commit(); // REMOVE FROM HERE
```

##### In `fintech_business_management` (`src/services/payments/paymentService.ts`):
* **Action:** Add a 5-minute Redis-backed Idempotency Lock on `(payer_account_id + amount + beneficiary_account_id)` or `X-Request-Id`.
* **Behavior:** If a duplicate payment request arrives while the first is in-flight or completed, immediately return the status of the first transaction instead of creating a second transfer.

##### In `fintech_webapp` (Frontend Back Office):
* **Action:** Disable the "Submit" / "Pay" button immediately upon click (`disabled={isSubmitting}`) to prevent operator double-clicking.

#### 2. Azure Database Modifications (`zb-psql-pp-prd-eastus`)

##### A. Scale PostgreSQL Hardware Sizing
* **Current:** `Standard_D2ds_v4` (2 vCPUs, 8 GiB RAM) — **98% CPU saturated**.
* **Action:** Upgrade to at least **`Standard_D8ds_v4` (8 vCPUs, 32 GiB RAM)** or `Standard_E8ds_v4` (Memory Optimized).
* **Command:**
```powershell
az postgres flexible-server update -g rg-purpleplum-prod-eastus -n zb-psql-pp-prd-eastus --sku-name Standard_D8ds_v4
```

##### B. Enable Azure Built-In PgBouncer
* **Current:** `pgbouncer.enabled = false`.
* **Action:** Enable PgBouncer on PostgreSQL Flexible Server to pool connections across all 24+ container pods.
* **Command:**
```powershell
az postgres flexible-server parameter set -g rg-purpleplum-prod-eastus -s zb-psql-pp-prd-eastus -n pgbouncer.enabled -v true
```

##### C. Apply Defensive Database Timeouts
* **Current:** `lock_timeout = 0`, `idle_in_transaction_session_timeout = 0`, `statement_timeout = 0`.
* **Action:** Set defensive thresholds to kill hanging transactions automatically:
```sql
ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
ALTER SYSTEM SET lock_timeout = '10s';
ALTER SYSTEM SET statement_timeout = '60s';
SELECT pg_reload_conf();
```

##### D. Enable High Availability (HA)
* **Current:** `highAvailability: Disabled` (Single Point of Failure).
* **Action:** Enable Zone-Redundant High Availability.
