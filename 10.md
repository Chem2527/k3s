## 1. Executive Summary

On September 3, 2026, during manual payment creation via the Back Office portal, an operator submitted an internal corporate transfer for Nexo Capital Inc. Due to severe database row lock contention and an uncommitted database transaction in `fintech_notifications_management`, the OTP verification request hung for approximately 60 seconds before returning `HTTP 410 ("Code cannot be accepted")`. 

Believing the first submission had failed, the operator requested a new OTP and re-submitted the transaction 2 minutes later. Consequently, **two duplicate transfers of $1,500,000.00 USD each** were executed and processed by Tuum core banking:

1. **Transaction 1 (`PAYM-212370`):**
   * **Timestamp:** `2026-09-03T17:52:00.147Z`
   * **Amount:** `$1,500,000.00 USD`
   * **Payer:** Nexo Capital Inc. (`ID-1015`)
   * **Beneficiary:** Nexo Financial LLC (`ID-134412`)
   * **Operator:** Biser Manchev
   * **Source Request ID:** `16600e0b-6b5e-4c32-abaf-1700e66cc277`
   * **Status:** `PROCESSED` in Tuum
2. **Transaction 2 (`PAYM-212372`):**
   * **Timestamp:** `2026-09-03T17:54:02.523Z` (2 minutes 2 seconds later)
   * **Amount:** `$1,500,000.00 USD`
   * **Payer:** Nexo Capital Inc. (`ID-1015`)
   * **Beneficiary:** Nexo Financial LLC (`ID-134412`)
   * **Operator:** Biser Manchev
   * **Source Request ID:** `bf515757-a2d8-4201-bc22-78a161d11537`
   * **Status:** `PROCESSED` in Tuum

Comprehensive analysis of Azure Log Analytics (`log-zb-pp-fintech-prod-eastus-001`), Application Insights (`insight-zb-purpleplum-prod-eastus`), and service codebases in Azure DevOps confirmed that this was caused by:
1. **Application Code Transaction Defect:** Uncommitted PostgreSQL transaction held open during slow external API calls in `otpService.ts`.
2. **Database Sizing Inversion:** Central PostgreSQL database server running on a tiny 2-vCPU instance (`Standard_D2ds_v4`), pegged at 94%–98.6% CPU.
3. **Missing Database Timeout Protections:** `lock_timeout = 0`, `idle_in_transaction_session_timeout = 0`, allowing queries to block for up to 12.4 minutes.
4. **Autoscaling Blind Spot:** Autoscaling rules only trigger on concurrent HTTP requests > 10, completely ignoring single-user hanging transactions.

## 6. Exact Code-Level Root Cause & The Fix

In `fintech_notifications_management` (`src/services/otp/otpService.ts`):

### The Defect:
```typescript
// Line 719: Explicit database transaction opened
const tranx = await connection.transaction();

// Line 735: Exclusive row lock acquired on the otps row
await OtpModel.query(tranx).update(queryParams).where("id", response.id);

// Lines 815-836: Outbound HTTP network requests executed while tranx is still OPEN
if (source === "PAYMENT" && payload?.payment_request_params) {
    const isApprovalFlow = await checkForApproval(payload); // Outbound HTTP
    const paymentResponse = await sendCreatePaymentRequest(payload, authToken); // Outbound HTTP
    responseObj.data = paymentResponse;
}

// Lines 849-855: Also identified in disableAuthenticatorApp
if (source === "MFA_DISABLE" || source === "MFA_ENABLE" || source === "MFA_DELETE") {
    const { data, message } = await disableAuthenticatorApp(authToken, source); // Outbound HTTP
}

// Line 857: Transaction NOT committed until after all external HTTP calls finish!
await tranx.commit();
```

### Why the False Error Occurred:
1. When the user clicked "Submit", request #1 hit `otpService.ts`. Line 674 immediately invalidated the OTP in Redis (`is_active = false`).
2. Request #1 then entered the database transaction and hung for 60 seconds while awaiting downstream payment processing.
3. Thinking the screen froze, the user clicked "Submit" a second time (request #2).
4. Request #2 hit Redis, saw the OTP code was already consumed (`is_active = false`), and threw **HTTP 410 ("Code cannot be accepted")**.
5. Request #1 completed in the background and sent the first $1.5M (`PAYM-212370`).
6. Believing the payment had failed, the user requested a fresh OTP and sent a second payment (`PAYM-212372`), resulting in a duplicate $1.5M transfer.

### The Permanent Code Fix:
1. **Commit Immediately:** Move `await tranx.commit();` immediately after Line 736 following the OTP update. Release the PostgreSQL row lock in **< 10 ms**.
2. **Execute External APIs Outside DB Transaction:** Never call outbound HTTP APIs (`sendCreatePaymentRequest`, `disableAuthenticatorApp`, etc.) while holding an open database transaction.
3. **Payment Idempotency Guard:** Add a 5-minute Redis idempotency lock in `fintech_business_management` on `(payer_id + amount + beneficiary_id)` to automatically reject duplicate submissions.

## 7. Current Setup Bottlenecks & Architectural Flaws in Zenus Production

| Category | Current Production Configuration | Severity | Risk & Impact |
| :--- | :--- | :--- | :--- |
| **Database Sizing Inversion** | PostgreSQL Flexible Server is `Standard_D2ds_v4` (**2 vCPUs, 8 GiB RAM**) serving 24+ container pods allocated 50+ vCPUs | **CRITICAL** | Database CPU is pinned at 94% – 98.6%. 2 vCPUs cannot handle lock arbitrations and 84 direct connections. |
| **PgBouncer Disabled** | Built-in PgBouncer is disabled on PostgreSQL (`pgbouncer.enabled = false`) | **HIGH** | Every container maintains its own direct Knex connection pool, exhausting connection slots and wasting CPU on context switching. |
| **High Availability Disabled** | High Availability is `Disabled` on `zb-psql-pp-prd-eastus` | **HIGH** | Single point of failure (SPOF) for the entire production banking platform. |
| **Zero Defensive Timeouts** | `idle_in_transaction_session_timeout = 0`, `lock_timeout = 0`, `statement_timeout = 0` | **CRITICAL** | PostgreSQL waits **forever** on locks (allowing the 12.46-minute lock hang). |
| **Autoscaling Blind Spot** | Only `concurrentRequests = 10` HTTP rule configured; no CPU, Memory, or Latency rules | **HIGH** | Slow transactions hanging for 60s never scale out because single-user request concurrency remains under 10. |
| **Code Transaction Scope** | Explicit DB transactions (`const tranx = await connection.transaction()`) wrap outbound HTTP network calls (`sendCreatePaymentRequest`, `disableAuthenticatorApp`) | **CRITICAL** | Holding row locks open while awaiting external HTTP APIs causes cascading thread locks across all microservices. |
| **Missing Idempotency Guard** | Payment endpoints lack Redis deduplication locks on `(user_id + amount + beneficiary)` | **CRITICAL** | User re-clicks on slow responses trigger duplicate multi-million-dollar banking transfers. |

## 8. Actionable Remediation Plan for Zenus Production

1. **Codebase Actions (Immediate):**
   * Commit `tranx.commit()` immediately after Line 736 in `fintech_notifications_management`.
   * Add Redis idempotency lock in `fintech_business_management` on payment request payloads.
   * Disable the UI "Submit" button upon click (`isSubmitting = true`) in `fintech_webapp`.
2. **Database Sizing & Engine Configuration:**
   * **Scale Up PostgreSQL:** Upgrade `zb-psql-pp-prd-eastus` from `Standard_D2ds_v4` (2 vCPUs) to at least **`Standard_D8ds_v4` (8 vCPUs, 32 GiB RAM)** or `Standard_E8ds_v4`.
   * **Enable PgBouncer:** Enable Azure built-in PgBouncer (`pgbouncer.enabled = true`) to pool connections across all microservices.
   * **Apply Defensive Timeouts:**
     ```sql
     ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
     ALTER SYSTEM SET lock_timeout = '10s';
     ALTER SYSTEM SET statement_timeout = '60s';
     SELECT pg_reload_conf();
     ```
   * **Enable High Availability:** Enable Zone-Redundant HA on `zb-psql-pp-prd-eastus`.
3. **Autoscaling Optimization:**
   * Add CPU and Memory scaling rules to Azure Container Apps (e.g. scale up when average CPU > 70% or average Memory > 75%).
   * Adjust HTTP concurrency scaling threshold from 10 to 5 for transactional services (`notifications-mgnt`, `business-management`).
