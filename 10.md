## 1. Executive Summary: What Is the Current Issue Today?

While the application code defect (uncommitted transaction in `otpService.ts`) has been **resolved and merged in PR #313**, the production environment is **actively suffering from severe infrastructure saturation and misconfigurations today (September 9, 2026)**:

1. **Massive Compute Sizing Inversion (4 vCPU Containers vs 2 vCPU Database):**
   * Each individual container app pod (e.g. `zb-prod-user-management-001`, `zb-prod-business-management-001`) has **4 vCPUs and 8 GiB memory** allocated at the container level.
   * With 24+ container pods across 12 microservices, the application layer has **over 50+ vCPUs and 100+ GiB RAM** blasting requests into the central database.
   * The central database (`zb-psql-pp-prd-eastus`) is a tiny **`Standard_D2ds_v4` instance with ONLY 2 vCPUs and 8 GiB RAM**.
   * A single container app replica has twice the compute of the entire database server! The 2-vCPU database cannot handle the query volume, locking requests and pinning database CPU at **98.4% – 99.14% today**.
2. **Azure PgBouncer Is Disabled (`pgbouncer.enabled = false`):**
   * All 24 container pods establish direct, unpooled TCP connections to PostgreSQL.
   * PostgreSQL allocates a dedicated Linux process per connection. With **84 active connections** competing for **only 2 CPU cores**, the database spends all its CPU context-switching between processes rather than executing queries.
3. **Database Connection Pool Status (Occupied vs. Left):**
   * **`max_connections` Limit:** Set to **`500`** in server parameters.
   * **Currently Occupied:** **`76 to 84` active direct connections** right now.
   * **Remaining Slots Left:** **`416` slots left** before hard connection exhaustion.
   * **The Trap:** While 416 theoretical slots remain, running 84 unpooled connections on a 2-vCPU server violates PostgreSQL best practices (optimal active connections on 2 cores is only 5 to 10). The 2 CPU cores are completely overwhelmed.
4. **No Lock Safeguards (`lock_timeout = 0`):**
   * Because PostgreSQL parameter `lock_timeout = 0` (wait forever), queries blocked by row locks are **actively stalling for 12 to 26.7 minutes today** instead of failing fast.
5. **Autoscaling Blind Spot (Why Container Apps Never Scaled):**
   * Container Apps have only one scale rule: `http-scaler: concurrentRequests = 10`.
   * An operator submitting a transfer or payment generates only **1 or 2 concurrent HTTP requests**.
   * Even when requests freeze for 60 seconds waiting on database locks, concurrency is only 1–2 requests, which never reaches the threshold of 10.
   * The autoscaler is completely blind to CPU exhaustion and slow queries, so **it never added a single replica**, keeping all services permanently stuck at the minimum of 2 pods.

### Issue C: Why the Current Autoscaling Rules NEVER Scale Container Apps
* **Current Production Rule:**
  * Rule name: `http-scaler`
  * Trigger: `concurrentRequests = 10`
  * Scaling range: Min replicas = `2`, Max replicas = `10`

#### Why It Never Triggered (The Blind Spot Explained):
1. **Single-Operator Concurrency is Low:** When an operator submits an internal transfer, payment, or OTP request in the Back Office portal, that action represents **1 single HTTP request** (or 2 if a background status poll runs).
2. **Hanging Requests Do Not Multiply Concurrency:** Even if that request freezes for 60 seconds waiting for database locks, the in-flight concurrency on that pod is still only 1 or 2 requests. Because $1 < 10$ and $2 < 10$, KEDA sees concurrency at 10%–20% of the threshold and concludes the container is completely idle.
3. **HTTP Scaler Cannot See Hardware or DB Delays:** The HTTP scaler has zero knowledge of container CPU, container memory, or database latency. If the database is freezing or Node.js event-loops are lagging, the HTTP scaler will **never add a single pod**.
4. **Outcome:** During peak load and during the September 3 incident, all services stayed at **exactly 2 replicas**.

## 3. What Rules Need to Be Added to Trigger Scaling on Memory & vCPU

To ensure Container Apps scale dynamically when load or processing increases, we must add **Multi-Metric Autoscaling Rules** directly in the Azure Portal:

| Rule Name | Rule Type | Metric Target | What It Does & When It Triggers |
| :--- | :--- | :--- | :--- |
| **`cpu-scaler`** *(NEW)* | Custom (`cpu`) | **`70%` Utilization** | Scales out new replicas whenever average pod CPU exceeds 70%, handling processing spikes. |
| **`memory-scaler`** *(NEW)* | Custom (`memory`) | **`75%` Utilization** | Scales out new replicas whenever memory exceeds 75%, preventing Out-Of-Memory (OOM) crashes when requests queue. |
| **`http-scaler`** *(MODIFY)* | HTTP | **`5` Concurrent Requests** | Lowered from 10 to 5, so smaller batches of concurrent user actions trigger scaling much faster. |

> **How Container Apps Evaluates Multiple Rules:** Azure Container Apps evaluates all rules and **scales out based on whichever rule requests the largest number of replicas** (the `MAX` formula). For example, if CPU spikes to 80% while HTTP concurrency is only 2, the app will scale out immediately!

## 4. After Enabling PgBouncer (`pgbouncer.enabled = true`), What Settings Must Change in Existing Container Apps?

When you turn on Azure Built-In PgBouncer, **you MUST update settings in the existing Container Apps** because PgBouncer listens on a different port:

### Setting 1: Change Database Port from 5432 to 6432
* **Direct PostgreSQL Port:** `5432`
* **Azure Built-in PgBouncer Port:** **`6432`**
* In each Container App's configuration / environment variables:
  * Update environment variable: **`DB_PORT = 6432`** (previously `5432` or default).
  * If the app uses a full connection URL (`DATABASE_URL`), change:  
    `postgres://user:pass@zb-psql-pp-prd-eastus.postgres.database.azure.com:5432/fintech`  
    to:  
    `postgres://user:pass@zb-psql-pp-prd-eastus.postgres.database.azure.com:6432/fintech`
* **What stays 100% UNCHANGED:**
  * Database Host stays identical: `zb-psql-pp-prd-eastus.postgres.database.azure.com`
  * Database Name stays identical: `fintech`
  * Database Username & Password stay identical.

### Setting 2: Adjust Node.js Application Connection Pool (Knex / pg)
* In `config/options.ts`, the application pool is configured:
  ```typescript
  pool: {
      min: Number(process.env.DB_MIN_CLIENTS) || 2,
      max: Number(process.env.DB_MAX_CLIENTS) || 10,
  }
  ```
* Because PgBouncer operates in **Transaction Pooling Mode**, Container Apps do not need large local connection pools.
* Set environment variable: **`DB_MAX_CLIENTS = 5`** (or `10`) per pod.
* With 24 pods having max 5 connections, at most 120 client connections hit PgBouncer, which PgBouncer translates into just 10–15 warm server connections to PostgreSQL.

### Setting 3: Zero-Downtime Migration
* On Azure PostgreSQL Flexible Server, **Port 5432 and Port 6432 work simultaneously**.
* Enabling PgBouncer does not close port 5432. You can enable PgBouncer on the database first, and then update container apps to port 6432 one by one without any downtime.

## 5. Step-by-Step Azure Portal UI Instructions (Strictly UI Click-Paths, Zero CLI)

Every verification and change can be done directly in the **[Azure Portal](https://portal.azure.com/)**:

### Action 1: Upgrade Database Sizing (Eliminates 100% CPU Bottleneck)
1. In the top search bar, type **`zb-psql-pp-prd-eastus`** and click it.
2. In the left navigation menu under **Settings**, click **Compute + storage**.
3. Under **Compute tier**, keep **General Purpose**.
4. Under **Compute size**, click the dropdown and select: **`Standard_D8ds_v4 (8 vCPUs, 32 GiB memory)`**.
5. Under **Storage size**, select **`256 GiB`** or **`512 GiB`** (boosts disk throughput from 500 up to 1,200–2,300 IOPS).
6. Click the blue **Save** button.

### Action 2: Enable Built-In PgBouncer
1. On the same `zb-psql-pp-prd-eastus` page:
2. In the left navigation menu under **Settings**, click **Server parameters**.
3. In the search box, type: **`pgbouncer.enabled`**.
4. Change the dropdown value from `false` to **`true`**.
5. Click **Save** at the top left.

### Action 3: Set Defensive Lock Timeouts (Stops 12–26 Minute Lock Freezes)
In that exact same **Server parameters** page:
1. Search: **`lock_timeout`** -> Change value from `0` to **`10000`** *(10 seconds in ms)*.
2. Search: **`idle_in_transaction_session_timeout`** -> Change value from `0` to **`30000`** *(30 seconds in ms)*.
3. Search: **`statement_timeout`** -> Change value from `0` to **`60000`** *(60 seconds in ms)*.
4. Click **Save** at the top left.

### Action 4: Update Container Apps to Connect to PgBouncer Port 6432
1. In the top search bar, search for your container apps: **`zb-prod-notifications-mgnt-001`**, **`zb-prod-business-management-001`**, **`zb-prod-user-management-001`**.
2. In the left menu under **Application**, click **Containers**.
3. Click the container named **`app`** -> click **Edit**.
4. Under **Environment variables**:
   * Add or edit **`DB_PORT`** -> set value to **`6432`**.
   * Add or edit **`DB_MAX_CLIENTS`** -> set value to **`5`**.
5. Click **Save** (this automatically triggers a rolling revision without downtime).

### Action 5: Add CPU & Memory Autoscaling Rules in Container Apps UI
1. On the Container App page, left menu under **Application** -> click **Scale and replicas** (or **Scale**).
2. **Update HTTP rule:** Click `http-scaler` -> change **Concurrent requests** from `10` down to **`5`** -> Click **Apply**.
3. **Add CPU rule:**
   * Click **+ Add rule** at the top.
   * **Rule name:** `cpu-scaler`
   * **Type:** Select **`Custom`**
   * **Custom rule type:** Enter `cpu`
   * **Metadata:**
     * Key: `type` | Value: `utilization`
     * Key: `value` | Value: `70`
   * Click **Add**.
4. **Add Memory rule:**
   * Click **+ Add rule** again.
   * **Rule name:** `memory-scaler`
   * **Type:** Select **`Custom`**
   * **Custom rule type:** Enter `memory`
   * **Metadata:**
     * Key: `type` | Value: `utilization`
     * Key: `value` | Value: `75`
   * Click **Add**.
5. Set **Min replicas:** `2` | **Max replicas:** `10`.
6. Click the blue **Save** button at the top.
